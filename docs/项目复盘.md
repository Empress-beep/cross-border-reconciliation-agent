# 项目复盘：跨境多平台订单 & 结算对账自动化 Agent

复盘目的：沉淀设计决策与经验教训，给出重新设计思路、现存不足、优化路线与企业化演进方向。

## 一、项目一页纸回顾

**交付物**：Web 对账工作台（浏览器上传 5 份报表 → 7 步流水线对账 → 差异 Excel + AI 归因 + Agent 问答）+ 对账引擎 `engine/` + 影刀文件契约旁路 + 29 项自动化测试 + 部署/运维/安全三份文档。

**关键事实**：

| 维度 | 数据 |
|---|---|
| 对账链路 | 订单↔结算、结算↔回款 双层，9 种对账状态 |
| 预期差异 | 9 处（订单侧 4 + 回款侧 5），金标准测试锁定 |
| 耗时 | 数小时人工 → 分钟级（样例全程约 1~3 分钟） |
| AI | 千问归因（先脱敏后出网）+ FastGPT RAG 问答；降级/熔断不阻断对账 |
| 质量 | pytest 29/29（golden 8 + AI 降级 4 + 聊天契约 17） |
| 稳定 | 15 分钟看门狗、僵尸任务兜底、双日志滚动归档 |

**做得对的三件事**：
1. **AI 是旁路不是主链路**——归因失败降级、连续失败熔断，对账主流程永远能出结果，这是财务场景的底线设计。
2. **金标准回归**——固定样例固定 9 处差异，任何重构跑一遍测试就知道有没有改坏对账逻辑。
3. **脱敏出网**——金额、账号先脱敏再调大模型，从架构上解决「原始财务数据能不能喂 AI」的问题。

## 二、如果重新编写这个项目

按七个层面给出重新设计的方案（假设从零开始、需求不变）：

### 1. 架构分层
- **现状**：`app.py` 同时承担路由、文件识别、任务队列、看门狗、AI 代理、静态服务（约 690 行），职责偏重。✅ **已落地（2026-10-31）**：拆为 `api/`（路由）+ `service/`（编排/存储/队列/看门狗），`app.py` 收敛为组合根。
- **重写**：拆 `api/`（纯路由与参数校验）→ `service/`（任务编排、上传识别、聊天代理）→ `engine/`（纯函数对账核，不依赖 Flask）。Flask 只做路由，引擎可独立 `python -m engine` 命令行运行，Web 只是外壳之一。

### 2. 任务调度与持久化
- **现状**：内存字典 + 线程池执行，重启任务丢失，靠看门狗与刷新兜底判终态。✅ **已落地（2026-10-31）**：MySQL `tasks` 表（条件更新状态机）+ Redis/RQ 队列（worker 自动守护），服务重启自动把 running/pending 恢复为 failed 并给出原因。
- **重写**：任务元数据落 SQLite/MySQL（任务表带状态机字段），执行用 RQ/Celery 或最小化 DB 轮询队列；重启自动恢复 `running` 任务为 `failed` 并给出原因；天然支持并发数控制与任务优先级。

### 3. 对账引擎与规则
- **现状**：9 种对账状态硬编码在 `checks.py` 的 if 链里，加一种差异类型要改代码。
- **重写**：规则配置化——YAML/JSON 定义「层级、匹配键、期望值表达式、阈值、状态文案」，引擎解释执行；差异类型成为数据而非代码。匹配从 pandas merge 升级为「先建索引再探测」，并预留分块处理，为百万行做准备。

### 4. AI 接入层
- **现状**：千问归因与 FastGPT 聊天两处各自处理超时/重试/错误，熔断器只覆盖归因。
- **重写**：统一 **LLM Gateway**——一处实现超时、重试、限流、熔断、成本统计、调用审计日志，两个业务场景共用；归因结果按「差异指纹」（差异类型+金额区间）做缓存，同一批差异重复跑不再重复花钱；接入层预留多模型切换（千问/DeepSeek/本地模型）。

### 5. 会话与上下文
- **现状**：聊天上下文为单批数据拼接的字符串，无历史会话。
- **重写**：结构化上下文对象 + 模板渲染；会话与消息落库，支持跨期追问（「上个月这个差异多吗」）；流式输出（SSE）替代长轮询等待。

### 6. 前端
- **现状**：Jinja + 原生 JS，轮询进度，差异表全量渲染。
- **重写**：最小组件化（Vue/htmx 二选一）；进度改 SSE 推送；差异表加分页、排序、筛选（按平台/状态/金额）；上传做前端预校验（文件数、后缀、关键字）减少服务端往返。

### 7. 测试与交付
- **现状**：29 项单测/契约测试，LLM 真实链路靠手动验收；Windows bat 启动。
- **重写**：CI（GitHub Actions）每次 push 自动跑 pytest；LLM 调用做录制回放（VCR 式 fixture），测试不依赖网络；补充 UI 端到端测试（Playwright 冒烟）；交付 Docker 镜像，`.env` 一处配置跨平台启动，摆脱 Windows/编码绑定。

## 三、不足与缺点（诚实清单）

### 架构与工程
1. **单进程内存队列**（✅ 已解决：MySQL + Redis/RQ 队列，重启任务不丢，架构支持并发扩展）。
2. **无数据库**（✅ 已解决：任务与元数据落 MySQL `tasks` 表）。
3. **`app.py` 职责过重**（✅ 已解决：拆分 api/ + service/ 分层）。
4. **Windows 绑定**：bat 启动、GBK 编码、本地路径假设，无法直接部署到 Linux 服务器。

### 功能与业务
5. **文件接入太死**：只认 5 类固定文件名的 `.csv`，平台改字段或加新平台就要改代码；无 xlsx、无 SFTP/邮箱自动收数。
6. **规则硬编码**：9 种状态写死在代码里，财务说「再加一条平台补贴校验」就得发版。
7. **无账期概念**：一次上传即一次任务，没有期次管理，无法按月查询历史、对比环比。
8. **无差异分级与审批**：所有差异平铺展示，缺「金额阈值分级 → 复核 → 放行」的财务工作流。
9. **币种/汇率处理弱**：样例单币种（USD），多币种折算、汇率来源与锁汇未覆盖。

### 数据、性能与安全
10. **性能未压测**：pandas 全内存单次加载，百万行真实报表行为未知。
11. **无鉴权**：局域网版任何能访问 8765 的人都能上传文件、下载财报，无登录、无角色、无操作审计——财务系统硬伤。
12. **观测薄弱**：只有文件日志，没有指标（任务耗时分位数、AI 成功率、失败原因分布），出问题靠翻日志。

### AI 应用
13. **归因成本线性增长**：逐差异调用无缓存，差异爆发期（大促后）费用与耗时同步上涨。
14. **问答无记忆**：单轮上下文，跨期、跨批次追问能力弱；回答准确性依赖知识库文档质量，缺答案评估手段。
15. **AI 质量无量化**：归因结论对不对只有人工肉眼判断，没有「命中率」统计口径。

## 四、优化与改进路线

### 近期（1~2 周，低成本高收益）
| 动作 | 说明 |
|---|---|
| ~~任务表落 SQLite~~ ✅ 已完成（2026-10-31） | 实际落地为 MySQL + Redis/RQ：任务表状态机、重启恢复、worker 自动守护 |
| 归因结果缓存 | 差异指纹去重，重复任务 AI 费用降为 0 |
| 进度 SSE 化 | 替换 2 秒轮询，体验与服务器负载双改善 |
| CI 自动化 | GitHub Actions 跑 pytest，杜绝回归裸奔 |
| 简单访问令牌 | `.env` 配 `ACCESS_TOKEN`，拦住局域网裸奔 |
| 差异表筛选 | 前端按平台/状态过滤，替代肉眼扫表 |

### 中期（1~2 月）
1. **规则配置化引擎**：差异类型进 YAML，财务可参与评审规则文本。
2. **统一 LLM Gateway**：重试/熔断/成本/审计一处实现，预留多模型。
3. **账期与期次管理**：按「平台+账期」组织任务，历史可查、可环比。
4. **Docker 交付**：镜像 + compose，Linux 服务器一条命令起。
5. **指标与告警**：任务失败率、AI 成功率、耗时分位数上监控，异常推企业微信/钉钉 webhook。
6. **会话落库**：聊天多轮记忆 + 跨期追问。

### 长期（企业化形态）
1. **权限与审计**：登录、角色（制单/复核/管理员）、操作审计日志，满足财务合规。
2. **系统集成**：结果回写 ERP（金蝶/用友/NetSuite）；RPA 从平台后台/邮箱自动收报表，替代手工导出。
3. **直连数据源**：平台 API / 银企直连拉流水，消灭手工上传环节。
4. **申诉闭环**：真实差异一键生成平台申诉工单并跟踪状态。
5. **运营看板**：对账时效、差异率、AI 命中率（人工复核抽样统计）可视化。

## 五、如何更贴近企业真实需求

企业财务要的不是「能跑的 Demo」，而是**可纳入日常账期流程的工具**。五个差距与对应做法：

1. **贴合财务节奏**：真实工作是日清（回款跟进）+ 月结（出账）。项目需增加账期维度与期次管理，SOP 明确「谁在什么时间点跑、复核什么、放行标准是什么」（见《SOP手册》）。
2. **差异要有处置流**：财务拿到差异后要分级（在途正常/需跟进/真实异常）、定责（平台/物流/己方）、审批后挂账或申诉。当前只到「展示与解释」，需补差异状态机与审批留痕。
3. **接真实报表字段**：平台真实导出（亚马逊 Settlement 报告、Temu 结算单）字段与样例未必一致，应做**字段映射配置层**——列名变化改配置不改代码；多币种、跨月在途、平台费用类目对齐会计科目。
4. **合规三件套**：登录鉴权、角色权限、操作审计（谁在何时对了哪期账、改了什么），加上数据保留期策略——财务系统的准入门槛，不是加分项。
5. **规模与稳定承诺**：给百万行压测报告、明确单次对账 SLA、定义失败重试与幂等规则（同账期重跑不产生重复结果）。企业评估的顺序是：数据安全 → 稳定 → 快，最后才是 AI。

**一句话总结**：这个项目已经证明了「Web 化 + 双层对账 + AI 旁路」的技术可行性；下一阶段的分水岭不在算法，而在**工程化（队列/数据库/权限）与业务化（账期/处置流/系统集成）**。
